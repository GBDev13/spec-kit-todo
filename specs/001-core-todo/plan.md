# Implementation Plan: Core Todo Functionality

**Branch**: `001-core-todo` | **Date**: 2026-03-12 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/001-core-todo/spec.md`

## Summary

Build a full-stack Todo application with full CRUD (Create, Read, Complete, Delete) for Todo items. The backend is a Node.js/Express/TypeScript REST API backed by SQLite (via Drizzle ORM). The frontend is a React/TypeScript SPA built with Vite, using a single `useTodos` hook for state and plain CSS for responsive styling.

## Technical Context

**Language/Version**: TypeScript 5.x (Node.js 20 LTS for backend; browser via Vite for frontend)
**Primary Dependencies**: Backend: Express 4, Drizzle ORM, better-sqlite3, Zod; Frontend: React 18, Vite 5
**Storage**: SQLite (file-based, durable, zero-infrastructure)
**Testing**: Vitest + supertest (backend); Vitest + React Testing Library + msw (frontend)
**Target Platform**: Node.js server + modern browser (Chrome, Firefox, Safari, Edge)
**Project Type**: Full-stack web application (REST API backend + SPA frontend)
**Performance Goals**: Todo list loads and is interactive within 2 seconds (SC-002); UI updates without page reload (SC-003)
**Constraints**: No auth; single-user; todo text max 500 chars; no offline support required
**Scale/Scope**: Single-user CRUD app; 4 API endpoints; 4 React components; 1 custom hook

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | Notes |
|-----------|--------|-------|
| I. Simplicity First | ✅ PASS | Express (not NestJS), plain CSS (not Tailwind), `useState` hook (not Redux/Zustand). No service layer or repository pattern in v1. |
| II. Core CRUD Completeness | ✅ PASS | All four operations covered: GET (Read), POST (Create), PATCH (Complete/Toggle), DELETE. Each backed by a persistent endpoint, reflected in UI, with error state. |
| III. Responsive & Polished UX | ✅ PASS | Plain CSS with mobile-first media queries. All 5 visual states designed: empty, loading, error, active, completed. |
| IV. Data Durability & Error Resilience | ✅ PASS | SQLite is ACID-compliant and durable across restarts. Zod validates all input at the API boundary. Frontend surfaces all errors to the user. |
| V. Future-Friendly, Not Future-Proof | ✅ PASS | `userId` nullable column in schema. Routes at `/todos` can be scoped to `/users/:id/todos` later. No auth implementation in v1. |

**Gate result: ALL GATES PASS.**

### Source Code (repository root)

```text
backend/
├── src/
│   ├── routes/
│   │   └── todos.ts          # Express router: GET /todos, POST /todos, PATCH /todos/:id, DELETE /todos/:id
│   ├── db/
│   │   ├── schema.ts         # Drizzle schema definition (todos table)
│   │   ├── index.ts          # DB connection + export
│   │   └── migrations/       # SQL migration files (generated by Drizzle)

│   │   └── todo.ts           # Shared TS types (Todo, CreateTodoInput, etc.)

├── tests/
│   └── todos.test.ts         # Vitest + supertest integration tests
├── drizzle.config.ts
├── package.json
└── tsconfig.json

frontend/
├── src/
│   ├── App.tsx               # Root: owns useTodos hook, renders layout
│   ├── components/
│   │   ├── TodoForm.tsx      # Text input + submit; calls onAdd prop
│   │   ├── TodoList.tsx      # Maps todos → TodoItem; renders empty/loading/error states
│   │   └── TodoItem.tsx      # Single row: text, toggle checkbox, delete button
│   ├── hooks/
│   │   └── useTodos.ts       # State: todos[], loading, error; actions: add, toggle, delete
│   ├── api/
│   │   └── todos.ts          # Thin fetch wrappers: getTodos, createTodo, toggleTodo, deleteTodo
│   ├── types.ts              # Todo interface: id, text, completed, createdAt, userId?
│   └── styles.css            # Global responsive styles
├── package.json
├── vite.config.ts
└── tsconfig.json
```

**Structure Decision**: Web application with separate `backend/` and `frontend/` packages at repo root. This keeps toolchains independent, allows either side to be replaced without touching the other, and clearly separates API from UI concerns.
